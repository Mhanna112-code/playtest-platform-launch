# Payments proof: recordings (Nov 2)

These clips show playtest-lite's money paths working against **Stripe TEST mode** with throwaway accounts (`rec+…@playtest.test`). Every clip pairs the app with a
small local viewer that reads the developer's PaymentIntents from Stripe's API with the test key. Next to each money step, `<name>.stripe.json` lists every
PaymentIntent of that developer: amount, status, `last_payment_error`, created and cancelled times, the Stripe dispute status, and the app rows that point at it.
`results-<scenario>.json` holds the run's own checks. `made.json` maps every file to its caption.

The rule that runs through every scenario (§125, merged): during a payment hold, **Pay what you owe** charges the debts and every charge waiting for the lift as ONE payment.
A chargeback hold's reservation covers both in the same way. Why a second charge can't happen on any path: [WHY-NO-DOUBLE-PAY.md](WHY-NO-DOUBLE-PAY.md).

## How it was run

- **Server.** A separate dev server on port 3480, run from the `pl-rec` worktree. It uses the `rec` schema of the local 5499 database and the `.env` Stripe test keys
  (checked to be `sk_test_`/`pk_test_`, never printed). Harness: `scripts/payments-proof/` (`serve.cjs`, `viewer.cjs` on 3481, `run.cjs <scenarios>`).
- **Card.** Test card **4000 0027 6000 3184**, which always asks the bank. It was saved through Stripe Checkout with Link unticked, and the bank's real 3D Secure test
  page was completed or left open in the browser.
- **Moving time.** Charge was opened by moving dates in the `rec` schema. A check's 3 days "run out" by moving its `actionBy` and running the clock
  (`confirm.expireActions`). For that reason, the run-out date in E7 reads Nov 2.
- **Chargebacks.** Stripe's webhook can't reach localhost, so a chargeback was opened by calling the function the webhook calls (`holds.chargebackOpened` with
  the PaymentIntent id, `appfn.mts`). Stripe itself therefore shows `stripe_dispute: none`; the app side (`chargeback=open`) is in the listings.
- **Earlier payment (H, I, J).** These scenarios needed an earlier payment that had already gone through (card 3184 always asks). It was made directly at Stripe with
  the 4242 test card and recorded as Cid's payment.
- **Old tabs (A, I, J).** An "old tab" is kept old by holding back its background refresh requests for those seconds. Without that, it would redraw or move to the
  dashboard on its next 20-second check before the press. The press itself goes to the server as usual.
- **Browser.** The recording Chrome runs with Local Network Access checks off. Without that, Stripe's 3D Secure page (a public site) can't return to the app on
  localhost ("The connection is blocked…"). This is a property of the local setup, not of the app.

## Bugs found while proving it (all fixed in §125, with tests in `tests/batch35-payment-proofs.test.ts`)

1. **Two reservations.** Two Pay what you owe presses at the same moment during a chargeback hold each reserved the full amount. The money was taken once on Approve,
   but the card was held twice. Reservations are now made under the developer's row lock.
2. **Listed twice.** Charges covered by a combined payment waiting for the bank also showed under "Charged once your tests resume" (seen in B's first recording).
3. **Check cut off by a reload.** A chargeback turning a payment hold into a chargeback hold reloaded the page while Pay what you owe's 3D Secure page was open, so
   the check could no longer be approved (seen in I's first recording). SessionWatch now waits while a bank check is open.
4. **Wrong first refusal.** A stale page's press during a new chargeback said "Verify your card first." It now stops once naming the chargeback first.

## Surprises, not money bugs

- **Wording after a chargeback.** J's stop box says "Press again to pay $22.00", but during a chargeback hold the second press first asks to verify the card, then
  *reserves* the amount rather than paying it.
- **Local environment.** The local Postgres crashed once during the run ("terminated by exception 0xC0000142", a Windows process-start failure). It recovered by
  itself, and the scenarios it interrupted were re-recorded. The dev server's worker restarted twice, and the harness now retries.
